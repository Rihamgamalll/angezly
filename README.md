# دَوْرك — Dawrak

منصة ويب مصرية (RTL/Arabic) لحجز الدكاترة وإدارة العيادات، وحجز مجموعات المدرسين وإدارة عدد الطلاب. هذا مشروع **Vite + React + TypeScript + Tailwind CSS + Supabase/PostgreSQL** قابل للاستكمال في محرّر كود. يحتفظ بالبنية الأصلية للمشروع المرفوع، ويضيف الصفحات التي كانت مفقودة، ولوحات تحكم، ومخطط قاعدة بيانات وعمليات حجز آمنة على مستوى قاعدة البيانات.

> **الحالة الحالية:** تم تجهيز كود التطبيق والمخططات SQL. **لا توجد مفاتيح Supabase أو اتصال فعلي بقاعدة بيانات ضمن الملف المرفوع**؛ لذلك لا يمكن الجزم أن الحجز يعمل على بيئة منشورة قبل التوصيل وتطبيق المهاجرات واختبارها. الصفحة العامة والمحاكاة التوضيحية يمكن فتحهما بدون اتصال، لكن الحجز الحقيقي يتطلب قاعدة بيانات فعالة.

## التشغيل

1. أنشئ مشروع Supabase **للتجربة أولاً**، أو اربط التطبيق بقاعدة Supabase الحالية الخاصة بمشروعك.
2. انسخ `.env.example` إلى `.env` وأدخل `VITE_SUPABASE_URL` و`VITE_SUPABASE_ANON_KEY` (مفتاح publishable/anon العام فقط). **لا تضع service_role في `.env` الخاصة بالمتصفح**.
3. من Supabase SQL editor، طبّق الملفات بالترتيب الزمني التالي:
   - `20261101124721_dawrak_core_schema.sql` (الجداول والوظائف والأدوار)
   - `20261101124752_dawrak_seed_demo_data.sql` **لبيئة الاختبار فقط** (بيانات خيالية قابلة للتمييز)
   - `20261101124814_revoke_handle_new_user_execute.sql`
   - `20261101140000_queue_attendance_security.sql`
   - `20261101150000_doctor_exceptions_notifications.sql`
4. من بيئة لديها اتصال بمستودع npm: `npm ci` ثم `npm run typecheck` ثم `npm run build` ثم `npm run dev`.
5. اضبط إعدادات Supabase Auth (رابط الموقع وروابط إعادة التوجيه وإثبات البريد الإلكتروني) لتطابق دومين المعاينة/النشر.
6. سجّل حسابك الشخصي من الموقع؛ لإنشاء أول **admin** شغّل SQL التالي **يدويًا من لوحة Supabase الموثوقة فقط** بعد استبدال الإيميل، ولا تضف هذا التنفيذ إلى المتصفح:

```sql
INSERT INTO public.user_roles (user_id, role)
SELECT id, 'admin' FROM auth.users WHERE email = 'OWNER_EMAIL_HERE'
ON CONFLICT DO NOTHING;
```

7. سجّل بحساب آخر كمدرس أو دكتور، وفعّل ملفه من `/admin` باستخدام حساب الإدارة؛ ملفات المحترفين الجديدة لا تنشر نفسها تلقائيًا.
8. افتح `/dashboard/teacher` لإنشاء مجموعة بسعة 3 طلاب، وافتح رابط المدرس `/teacher/[slug]` في جلسات حسابات مختلفة للتحقق من تزامن الحجوزات وإغلاق المجموعة.

## أهم المسارات

- `/`: الصفحة الرئيسية واختيار الخدمة.
- `/doctors` و`/teachers`: البحث والتصفية.
- `/doctor/[slug]` و`/teacher/[slug]`: صفحة احترافية برابط قابل للمشاركة.
- `/join`, `/register/doctor`, `/register/teacher`: تسجيل أصحاب الخدمات.
- `/signup`, `/login`: الحسابات.
- `/dashboard`: حجوزات المستخدم ومتابعة دوره.
- `/dashboard/doctor`: مواعيد الطبيب، الإجازات، حالات الحجوزات والدور.
- `/dashboard/teacher`: المجموعات، السعة، إضافة طالب يدويًا، تسجيل حضور وتغييرات الجدول.
- `/admin`: اعتماد/إيقاف ملفات الدكاترة والمدرسين.
- `/notifications`: إشعارات داخل النظام بعد ربط قاعدة البيانات.
- `/demo`: **محاكاة مستقلة بوضوح عن قاعدة البيانات** توضح إغلاق مجموعة مكوّنة من ثلاثة أماكن بدون بيانات شخصية.

## الاحترازات التقنية

- العمليات المهمة `book_appointment`, `enroll_in_group`, `teacher_add_enrollment`, `cancel_group_enrollment` تعمل من SQL RPC مع قفل الصف/القيود. الواجهة وحدها لا تفرض السعة.
- حظر ازدواج حجز الطبيب يشمل تقاطع الفترات الزمنية (بعد تطبيق أحدث migration).
- بيانات تسجيل الطلاب والمرضى خاصة وتُحمى بسياسات RLS، ولا تظهر للزوار العامة.
- اختيار العطلات من لوحة الطبيب يوقف الحجوزات الجديدة، ويرفض تحديد يوم إجازة فيه حجوزات سابقة نشطة دون التعامل معها.
- رابط واتساب يفتح مشاركة من المستخدم نفسه؛ **لا يرسل رسائل واتساب تلقائيًا**.
- بيانات Seed خيالية وأسماء وصور تمثيلية، لا تخص مهنيين موثقين؛ **لا تشغّل seed في الإنتاج**.
- صفحات المدربين والدكاترة تعمل بروابط حسب slug، مع أصل الدومين الحالي. معاينات Open Graph الفردية على الشبكات الاجتماعية تحتاج توليد metadata من السيرفر أو وظيفة استضافة خاصة.

## الاختبارات اللازمة قبل الإطلاق

- التسجيل والتأكيد والدخول والخروج.
- اعتماد ملف دكتور ومدرس من حساب admin مستقل.
- حجز طبيب، إعادة فتح الموقع والتحقق من اختفاء الموعد.
- حجز نفس الميعاد من جلستين معًا (يُقبل واحد فقط).
- تسجيل الحضور في يوم الكشف، وتقدّم الدور ورؤية تحديثه في حساب المريض.
- إنشاء مجموعة بسعة 3، وحجز 3 طلاب، ثم التأكد أن الرابع رُفض واقتُرحت بدائل.
- اختبار محاولة حجز آخر مقعد بالتوازي؛ ثم إلغاء مكان وعودة المقعد.
- فصل الصلاحيات: مدرس آخر لا يستطيع قراءة قائمة طلاب المدرس الأول، وطبيب آخر لا يستطيع قراءة مرضاه.
- التحقق من سلوك العطلات، ومن تغيير مدة الكشف والجداول أثناء وجود حجوزات.
- اختبار أوقات القاهرة وواجهة الهاتف، وفشل الشبكة وتأخير الاستجابة.
- تشغيل `npm run typecheck` و`npm run build` و`npm run lint` في بيئة بها dependencies.

## ما لم يكتمل ويحتاج مرحلة لاحقة

من المهم جدًا عدم اعتبار الملف إطلاقًا إنتاجيًا مكتملًا. يلزم تطوير واختبار إضافي في: حجوزات متعدد الأطباء داخل مركز واحد وإدارة الموظفين والصلاحيات الدقيقة، إعادة الجدولة الذرّية، تذكيرات الرسائل الخارجية SMS/WhatsApp/Email، المراجعات والتقييمات الموثقة وإدارة الشكاوى، المدفوعات والاشتراكات الحقيقية، تقارير مالية شاملة، إدارة التخصصات والمحافظات من لوحة الإدارة، نظام إشعارات للمتابعة المؤقتة، معاينات OG المولّدة على السيرفر، اختبارات التكامل والتزامن الفعلية، مراجعة الخصوصية والامتثال، وإجراءات التحقق من مؤهلات الأطباء. هذه أجزاء مهمة من الخطة الأصلية، ولا ندّعي أنها منتهية.
